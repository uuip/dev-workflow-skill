本轮属于集成测试阶段。

本阶段目标：
验证本次功能在真实或接近真实的基础设施中，能从业务流程入口走到流程结束。

这不是单元测试。
这不是只测某一个函数。
这不是只测某一个接口。
这不是用 mock 拼出来的测试。

输入：
1. 已确认的软件设计文档
2. 已确认的开发任务和验收标准
3. 已完成的代码改动
4. 已通过的 TDD 测试结果
5. 项目已有的本地运行方式、测试方式和依赖服务说明

基础设施要求：
1. 优先使用项目已有的真实测试基础设施。
2. 如果项目已有 docker compose、testcontainers、测试数据库、测试 Redis、测试 Nginx、测试消息队列等配置，优先复用。
3. 集成测试应使用真实 PostgreSQL / MySQL / Redis / Nginx / 消息队列 / 对象存储等依赖，除非项目本身没有相关依赖。
4. 不允许为了方便而把外部依赖全部 mock 掉。
5. 不允许只验证内存逻辑。
6. 不允许只调用单个接口后就认为集成测试完成。

外部资源规则：
1. 如果测试需要 API key、token、账号、私有服务、人工登录、付费资源、真实第三方环境或类似外部资源，必须停下来等待用户提供。
2. 不要伪造这些资源。
3. 不要跳过这些测试。
4. 只有在用户明确同意时，才可以把对应检查记录为“未验证”。

测试设计要求：
1. 先识别本次功能的完整业务流程入口和结束条件。
2. 先列出本次新增或修改的核心业务流程覆盖清单。
3. 每个核心业务流程至少要有 1 条完整成功路径，除非明确说明不适用并获得用户确认。
4. 设计至少一个贯穿完整业务路径的测试场景。
5. 测试必须覆盖多个系统边界或组件交互。
6. 测试必须验证真实数据写入、查询、状态变化和清理结果。
7. 测试必须包含正常流程。
8. 如果当前需求涉及权限、状态流转、重复提交、并发、缓存、异步任务或外部服务，也必须设计对应集成测试。
9. 测试结束后必须清理测试数据，或使用可隔离的测试数据库、命名空间或事务策略。

示例测试粒度：
- 添加用户 -> 查询用户 -> 删除用户 -> 再尝试登录
- 创建订单 -> 支付回调 -> 查询订单状态 -> 重复回调 -> 退款
- 上传文件 -> 查询文件列表 -> 下载文件 -> 删除文件 -> 再次访问应失败
- 创建审批单 -> 审批通过 -> 状态变更 -> 权限校验 -> 审计日志写入

禁止：
1. 不要把单元测试包装成集成测试。
2. 不要只测试单个 repository、service、controller 或接口。
3. 不要只验证 HTTP 200。
4. 不要只验证函数返回值。
5. 不要使用 mock 代替本阶段需要验证的真实基础设施交互。
6. 不要因为缺少外部资源就静默跳过。
7. 不要为了测试新增生产无关抽象。

执行步骤：
1. 阅读项目已有测试结构和运行方式。
2. 识别本次功能涉及的真实依赖：数据库、Redis、Nginx、消息队列、对象存储、第三方服务等。
3. 说明准备复用哪些已有测试基础设施。
4. 列出本次新增或修改的核心业务流程覆盖清单。
5. 设计完整业务流程测试场景。
6. 明确每个场景的入口、步骤、断言、数据准备和数据清理方式。
7. 如果缺少必要外部资源，停止并列出缺失内容，等待用户提供。
8. 编写或补充集成测试。
9. 运行集成测试并读取完整输出和退出码。
10. 如果失败，说明失败原因，并回到实现阶段修复。
11. 如果通过，输出测试证据。

Gate：
1. 已列出本次新增或修改的核心业务流程覆盖清单。
2. 每个核心业务流程都有完整成功路径覆盖，或明确记录未覆盖原因并获得用户确认。
3. 涉及权限、状态流转、重复提交、并发、缓存、异步任务或外部服务的流程，已有对应覆盖或明确记录未覆盖原因并获得用户确认。
4. 集成测试使用真实或项目认可的本地基础设施。
5. 集成测试命令已运行，完整输出和退出码已读取。
6. 测试数据准备和清理方式明确。
7. 没有阻塞性的集成测试失败。
